Build to spec,
not to guesswork. 讓 AI 照規格做，
而不是照猜測做。

Code with AI long enough and you hit the same thing. You toss out "build me a login feature," it starts writing code immediately, and halfway through you realize the database, error handling and edge cases it assumed are all wrong. Or it says "bug fixed" — but it still breaks on run, and now there's a side effect somewhere else too. Given a vague wish, an LLM can only fill the gaps with whatever looks plausible. 用 AI 寫程式久了，大概都遇過同一件事。丟一句「幫我做個登入功能」，它馬上開始寫 code， 寫到一半才發現它假設的資料庫、錯誤處理、邊界條件全都不是想要的。或者它說 「bug 修好了」，但一跑還是壞的，甚至某個地方又出現副作用。 一句模糊的願望，LLM 只能用「看起來合理」的東西填補空白。

My approach: write the spec clearly before you start, so the AI builds to spec instead of guessing. Here's how I open every new project. 我的作法是：開工前先把規格寫清楚，讓 AI 照規格做，而不是瞎猜測做。 下面是我每個新專案的起手式。

§ 01 · Step one § 01 · 第一步

Start with Git. 先建 Git。

The very first thing in a new folder is git init. 開新資料夾第一件事就是 git init。

Claude Code has its own rewind / checkpoint mechanism — it snapshots your files before each prompt, and a double-tap of Esc rolls them back. Handy, but it only tracks Claude's edits (not what you ran by hand), and it can't cross machines, branch, or support collaboration. It's a tool for "undo within this session," not version control. Claude Code 自己有 rewind / checkpoint 機制， 每個 prompt 前會自動 snapshot 檔案，按兩下 Esc 就能倒回去。方便，但它只追蹤 Claude 的改動，不含你手動跑的東西，也不能跨機器、不能開分支、不能多人協作。 它是「這次 session 內反悔」的工具，不是版本控制。

Git fills the gaps: Git 補足了：

  • branch — one per feature / issue; botch it, delete it, start over, and the mainline stays clean. branch：每個 feature / issue 開一條，做壞了砍掉重來，主線永遠乾淨。
  • Full history — every commit ties to a ROADMAP step, so three months later you can still trace why it was written this way. 完整歷史：每個 commit 連到一個 ROADMAP 步驟，三個月後還能追為什麼這樣寫。
  • Reviewable diffs — a reviewer (human or AI) sees only what changed, not the reasoning that produced it. 可回溯的 diff：reviewer（人或 AI）只看改了什麼，不看產生改動的推理過程。
  • Across sessions / machines — close the terminal and checkpoints are gone; only git remains. 跨 session / 跨機器：checkpoint 關掉終端就只剩 git。
§ 02 · Step two § 02 · 第二步

Talk it through with AI,
produce three documents. 跟 AI 反覆討論，
產出三份文件。

Before starting, I go back and forth with the AI, aiming to produce three spec documents. 開工前會跟 AI 來回討論，目標是產出三份規格文件。

SPEC.md requirements as unambiguous sentences 把需求寫成沒有歧義的句子

The biggest problem with requirements is "I thought I was clear." Use EARS (Easy Approach to Requirements Syntax) to recast each requirement into a WHEN / THEN / SHALL structure: 需求最大的問題是「我以為我講清楚了」。用 EARS（Easy Approach to Requirements Syntax） 把每條需求轉成 WHEN、THEN、SHALL 的結構：

WHEN a user enters the wrong password 5 times in a row, THEN the login system SHALL lock the account for 15 minutes. WHEN 使用者連續輸入錯誤密碼 5 次，THEN 登入系統 SHALL 鎖定帳號 15 分鐘。
SDD.md how the system is built 系統怎麼長

SPEC says "what to build"; the SDD (Software Design Document) says "how." Here you fix the system architecture, data structures, data flow, error handling, and the automated tests and acceptance criteria. SPEC 講「要做什麼」，SDD（Software Design Document）講「怎麼做」。在這裡定下系統架構、 資料結構、資料流程、錯誤處理、以及自動測試與驗收標準。

The most valuable part of this document is error handling and acceptance. AI is great at the happy path; what it most often misses is "what happens when it fails" and "what counts as done." Write those two into the SDD before touching code, and they won't turn into hard-to-trace bugs later. 這份文件最值錢的地方是錯誤處理跟驗收。AI 很會寫 happy path， 最容易漏的就是「出錯時怎麼辦」和「怎麼算做完」。把這兩塊在動手前就寫進 SDD， 後面才不會變成難以追蹤的 bug。

ROADMAP.md broken into trackable steps 拆成可追蹤的步驟

Break implementation into a numbered checklist of steps, each small enough to finish and verify on its own, each linked to its git commit. 把實作拆成編號步驟 checklist，每步小到可以獨立完成、獨立驗證，並且連到對應的 git commit。

The key is that the numbers stay permanently stable. Once it's in the ROADMAP, issue/12 is always Step 12; to split it, use 12a / 12b — never renumber. For steps you won't do, leave a placeholder with one line on why, instead of silently deleting them. Then half a year later, every commit in git log still maps back to the original plan. 關鍵是編號要永久穩定。一旦寫進 ROADMAP，issue/12 永遠是 Step 12，要拆分用 12a / 12b，不重新流水號；不做的步驟留 placeholder 加一行說明為什麼不做，不要默默刪掉。這樣半年後翻 git log， 每個 commit 都還對得回當初的規劃。

§ 03 · Step three § 03 · 第三步

Write a project-level
CLAUDE.md. 寫專案層級的
CLAUDE.md。

CLAUDE.md is the contract the AI reads at the start of every session. Use it to keep the three documents above always up to date: require the AI, on finishing each ROADMAP step, to go back, tick the matching checkbox, and update the "Currently working on" line at the top. CLAUDE.md 是 AI 每個 session 開頭都會讀的契約。用它來確保上面三份文件的狀態 永遠 up to date：規定 AI 每完成一個 ROADMAP 步驟， 就要回去把對應的 checkbox 打勾、把頂端的「Currently working on」更新。

Writing a CLAUDE.md has a counterintuitive rule: shorter is better. The official guidance is under 200 lines; past 300, the AI starts dropping signals. The test for each line is "if I removed this, would the AI make a mistake?" — if not, cut it. A bloated CLAUDE.md isn't safer; it drowns the rules that actually matter in noise. 寫 CLAUDE.md 有個反直覺的原則：越短越好。官方建議 200 行內， 超過 300 行 AI 開始遺漏信號。判斷標準是每一行都問自己「拿掉這行，AI 會犯錯嗎？」 不會就砍掉。膨脹的 CLAUDE.md 不是更安全，是讓真正重要的規則被雜訊淹沒。

§ 04 · Step four § 04 · 第四步

Build with Skills. 搭配 Skill 開發。

A Skill is an on-demand workflow; CLAUDE.md is an always-on rule. Putting skill-shaped things into CLAUDE.md just wastes context. My regular set: Skill 是按需載入的工作流，CLAUDE.md 是永遠開著的規則。該放 skill 的東西放進 CLAUDE.md 只是白白佔 context。我固定搭這幾個：

AskUserQuestion

When producing the SDD, I let the AI interview me instead. I give a minimal description and have it use this tool to ask — one at a time — about technical implementation, UI, edge cases and trade-offs, drilling into points I hadn't even thought of, and only then write the SDD. 產 SDD 時讓 AI 反過來訪談我。我給最小的描述，叫它用這個工具一條一條問技術實作、UI、 邊界條件、取捨，問到我自己都沒想過的點，最後才寫成 SDD。

test-driven-development

From obra's superpowers. It enforces Red-Green-Refactor: write a failing test first, then write code to pass it, no skipping steps. Before the test you ask "what should this do"; after, "what does it actually do" — two different questions. With a test that passes / fails, the AI can run its own verification loop. 來自 obra 的 superpowers。 強制 Red-Green-Refactor：先寫會失敗的測試，再寫 code 讓它通過，不准跳步。測試前問的是 「這東西應該做什麼」，測試後問的是「這東西實際做了什麼」， 這是兩個不同的問題。有了會 pass / fail 的測試，AI 就能自己跑驗證迴圈。

karpathy-guidelines

Karpathy's four general principles: think before writing, simple first, surgical changes, goal-driven execution. A cure for AI over-design, drive-by edits to unrelated code, and needless layers of abstraction. Karpathy 整理 的四條通用準則：先想再寫、簡單優先、外科手術式改動、目標驅動執行。專治 AI 過度設計、 順手改不相干的 code、加多餘的抽象層。

obsidian-vault

A note-taking skill I built so Claude understands my Obsidian folder structure (Inbox for scratch, Notes for my own writing, Resource for external material, Index for topic indexes). Pitfalls, decisions and research insights from development get filed and turned into notes automatically. When the project's done, the knowledge settles with it — instead of getting lost in chat logs you can't fish back out. 自建的筆記 skill，讓 Claude 懂我的 Obsidian 資料夾結構（Inbox 暫存、Notes 自寫、 Resource 外部、Index 主題索引），開發過程中的踩坑、決策、研究心得都能自動歸位整理成筆記。 專案做完，知識也跟著沉澱下來，不會散在對話紀錄裡撈不回來。

§ 05 · The point § 05 · 收束

Why bother with all this. 為什麼要這麼麻煩。

Writing three documents, setting up skills, insisting on stable ROADMAP numbers — it looks like it slows down the start. But the real value of this process isn't the "documents" themselves; it's that it forces you to think a vague idea through. 寫三份文件、設 skill、堅持 ROADMAP 編號，看起來像在拖慢開工。但這套流程真正的價值不在 「文件」本身，而在它逼你把模糊的想法想清楚。

AI amplifies discipline; it doesn't replace it. Give it a clear spec and it implements at 10×; give it a vague wish and it produces, at 10×, something that looks right and is entirely wrong — and you spend even more time cleaning up. AI 放大的是紀律，不是取代紀律。你給它清楚的規格，它幫你十倍速實作；你給它模糊的願望， 它十倍速產出看起來對、實際全錯的東西，你還得花更多時間清理。

For me, the most useful part of this opening ritual isn't the filenames — it's that it turns "developing with AI" from "throw a request → get a blob of code → patch back and forth" into "align on spec → AI runs to spec → I sign off." The former is gambling; the latter is engineering. 對我來說，這套起手式最有用的部分不是那幾個檔名，而是它讓「跟 AI 開發」從 「丟需求 → 收一坨 code → 來回修」變成「先對齊規格 → AI 照規格跑 → 我驗收」。 前者是賭運氣，後者是工程。

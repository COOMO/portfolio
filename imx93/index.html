Problem問題

  • A board maker ships an i.MX93 product whose Linux system one engineer had built with Yocto. After that engineer left, nobody could reproduce the build.一家板廠出貨的 i.MX93 產品，Linux 系統是一位工程師用 Yocto 建的。他離職後，沒人能重現建置。
  • The shipped image was unstable under load, and nobody could change it.出貨映像在高負載下不穩，而且沒有人能改它。
  • More boards were coming, and each needed the same system, its own MAC pair and a record that it passed.後面還有更多板子要出。每一塊都要裝同一套系統、燒各自的 MAC，並留下通過驗收的紀錄。

Solution解法

  • I rebuilt the whole chain from NXP's LF6.18.20 sources: SPL, TF-A, OP-TEE, U-Boot and kernel 6.18.20 with the board's own device tree, so no vendor binary remains.整條鏈從 NXP 的 LF6.18.20 原始碼重建：SPL、TF-A、OP-TEE、U-Boot，加上配板子自己 device tree 的 kernel 6.18.20，沒有留下任何原廠 binary。
  • Two payloads: a Debian maintenance system on p1 and the Ubuntu main system on p2, and either one can reinstall the other.兩個 payload：p1 放 Debian 維護系統，p2 放 Ubuntu 主系統，任一邊都能重灌另一邊。
  • An install line in Python turns a factory board into a unified one in about three minutes, with no serial cable. A web page runs it for many boards at once.Python 寫的安裝線，約三分鐘把出廠板裝成統一版，不需要 serial 線。網頁版可以同時處理很多塊板。

Key screens主要畫面

Install station裝機站

  • Every board that asks for DHCP becomes a card: factory, unified, busy or offline.每塊發出 DHCP 請求的板子都會變成一張卡：出廠態、統一版、作業中或離線。
  • A factory card has one button. It suggests the next MAC from the purchased block and a board name, then runs the full conversion with progress and a final checkup.出廠卡只有一個按鈕。按下去它會從購買的號段建議下一組 MAC 與板名，接著跑完整改裝，過程顯示進度，最後自動 checkup。
  • A unified card offers reinstall, checkup, dtb update, set MAC, file upload and download, and reboot.統一版卡提供重灌、checkup、更新 dtb、設定 MAC、上傳下載檔案與重開機。
  • Three faults get a badge on the card: a blank RS-485 EEPROM, an interrupt storm, a station NIC without its address.三種故障會在卡片上亮標記：RS-485 EEPROM 空白、中斷風暴、站台網卡沒有設位址。

Install line安裝線

DHCP
The PC is the DHCP server, so a factory board shows up as soon as it asks for an address. Boards are identified by SoC serial because the MAC changes during install.PC 當 DHCP server，出廠板一要位址就會現身。板子用 SoC 序號識別，因為 MAC 在安裝過程中會改變。
p1 · maintenance維護系統
The station pushes the payload and the installer over SSH; nothing on p2 is touched yet.站台透過 SSH 把 payload 與安裝器推上去，這時 p2 還沒有動。
Install安裝
Repartition, write p2, write the bootloader and the MAC pair, read everything back, hash.重建分割、寫入 p2、寫 bootloader 與 MAC 對，全部回讀並算 hash。
RS-485 EEPROM
Checked; burned if blank.檢查，空白就補燒。
checkup
VERDICT, record, baseline.VERDICT、紀錄、baseline。
  • Asset names are the interface: kernel, modules, payload, each with its own .sha256 and size file. One installer handles both the factory conversion and a plain reinstall.發布檔名就是介面：kernel、modules、payload，各自配一個 .sha256 與大小檔。同一支安裝器既做出廠改裝，也做一般重灌。
  • Every write is read back and hashed before the board reboots. On a mismatch the installer stops and keeps the shell.每次寫入都先回讀算 hash，對了才重開機；不符就停在 shell，保留現場。
  • The board keeps one IP for the whole job, and the station reserves that IP for the new MAC before the board changes identity, which is what lets several installs run at once.一塊板在整個作業中都用同一個 IP，板子換身分之前站台就先把這個 IP 預留給新 MAC，多塊板才能同時安裝。
  • A job that fails resumes from its phase. A job that succeeds is not re-run, and a backup equal to a known asset is not kept twice.失敗的作業從停下的那個階段續跑；成功的作業不重跑，和已知發布檔相同的備份也不會留第二份。
  • The page and the CLI share the same job code; the page only wraps it.頁面與 CLI 共用同一份作業碼，頁面只是外面的一層包裝。

Found and fixed找到並修正的問題

What turned up while rebuilding, and what fixed it. Each item was verified on the original board before and after.重建過程中找到的問題與修法。每一項都在原板上做過修前修後的對照。

Interrupt storm中斷風暴

  • A PMIC interrupt was routed to the wrong pad in the device tree and fired at 9 kHz. Rerouting it brought dmesg errors to zero and stopped the panic under load.device tree 把 PMIC 的中斷線接到錯的 pad，每秒觸發 9 千次。改正之後 dmesg 錯誤歸零，高負載 panic 也消失。
  • The station still watches for it and raises a badge on the card.站台持續監看，再發生就在卡片上亮標記。

DRAM timingDRAM timing

  • The DRAM is plain LPDDR4 rated to 3200 MT/s, and the original bootloader clocked it faster than that. The rebuilt bootloader uses the part's rated timing.板上的 DRAM 是額定 3200 MT/s 的 LPDDR4，原本的 bootloader 把它跑得比額定快。自建版改用顆粒額定的 timing。

RS-485 direction pinRS-485 方向腳

  • On some boards the USB-serial bridge's EEPROM was blank, which left the RS-485 direction pin undefined. A four-port loopback jig found it.部分板子的 USB 轉序列橋接晶片 EEPROM 是空白的，RS-485 的方向腳因此沒有定義。這是用四埠回送治具找到的。
  • Every install path now programs it and checkup verifies it; fielded boards were brought up to date with the same tool.現在每條安裝路徑都會燒好，checkup 也必檢；已出貨的板子用同一支工具補齊。

Interface names flip網路介面名對調

  • end0 and end1 are numbered differently on Debian and Ubuntu, so the network self-setup picks the port by carrier instead of by name.end0 與 end1 在 Debian 和 Ubuntu 上的編號相反，網路自動設定因此改成依 carrier 選埠，不寫死介面名。

NPU userspaceNPU userspace

  • The NPU userspace could not run inference: an outdated delegate, firmware in the wrong path and no Python runtime. All three are fixed, and fielded boards upgrade with one .deb.NPU 的 userspace 跑不了推論：delegate 過舊、韌體放錯位置、沒有 Python runtime。三項都修好了，已出貨的板子裝一個 .deb 就能升級。

OP-TEE and TPMOP-TEE 與 TPM

  • BL32 and TPM2_Startup were absent from the boot chain. With them added, the TPM appears as /dev/tpm0 and checkup reads PCR0.開機鏈原本沒有 BL32 與 TPM2_Startup。補上後 TPM 以 /dev/tpm0 出現，checkup 會讀 PCR0。

Delivery交付

  • The customer repo holds the tool, the README and small files, while kernel and images live in a GitHub Release. fetch-assets.py downloads them and verifies every file against the committed sha256 ledger.客戶 repo 放工具、README 與小檔案，kernel 與映像放在 GitHub Release。fetch-assets.py 下載後逐檔對照已提交的 sha256 校驗清單。
  • A GitHub Action re-checks the ledger against the Release on demand, because re-uploading an asset emits no event.GitHub Action 可以手動重新比對校驗清單與 Release，因為重新上傳發布檔不會觸發任何事件。
  • LICENSES.md lists every component, its license and where the source is.LICENSES.md 列每個元件、授權與原始碼位置。
  • The customer's three steps are capture, install, checkup. The README gives the exact commands and the expected last line of each.客戶要做的三步是 capture、install、checkup。README 給出確切指令，以及每一步預期看到的最後一行。
  • The MAC ledger is one Markdown table that the station appends to, and it is the record of which board got which pair.MAC 配號表是一張 Markdown 表，由站台自動追加，哪塊板拿了哪組號都查得到。
  • The same skeleton was reused for U5 genio 420: change the board files and keep the station, the ledger and the release flow.同一副骨架在 U5 genio 420 再用了一次：換掉板子專屬的檔案，站台、配號表與發布流程都不用動。
